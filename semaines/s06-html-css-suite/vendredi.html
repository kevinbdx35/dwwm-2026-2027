Vendredi 13/11 — Vérifier sa page, puis la corriger

Formateur

Kevin Bardoux

Date de publication

vendredi 13 novembre 2026

Compétences visées : C3 · apprendre en continu (veille)
Livrable : votre page publiée, vérifiée et corrigée ; une entrée de plus dans votre journal de veille.

ImportantLe minimum du jour
  • Les trois contrôles faits sur votre page publiée, les corrections republiées.
  • Une entrée de plus dans votre journal de veille.

Le reste (rubrique « Si le temps le permet » et encadrés « Défi ») est la suite naturelle, pour ceux qui avancent.

Objectifs

  • Vérifier sa page : Lighthouse, clavier, contraste.
  • Corriger, puis republier.
  • Savoir vérifier qu’une propriété CSS est utilisable aujourd’hui.

Veille — Une propriété CSS est-elle utilisable ? (30 min)

En groupe (15 min)

  1. Groupe 1 : sur MDN, que veut dire Baseline ?
  2. Groupe 2 : Widely available et Newly available : quelle différence ?
  3. Chaque groupe : une propriété de la semaine, et son statut.
  4. Dans chaque groupe : un lecteur, un secrétaire, un porte-parole.

Source en anglais : la page Baseline (compatibility) de MDN (MDN contributors, s. d.). Si vous préférez travailler seul, faites les trois questions seul et donnez votre réponse par écrit.

Mise en commun et journal de veille (15 min)

  1. Chaque porte-parole présente ce que son groupe a trouvé (3 min).
  2. Seul : ajoutez l’entrée du jour à votre journal de veille.

Matin — Vérifier sa page : Lighthouse, clavier, contraste

Rappel (5 min)

  1. dwwm-tp est-il public ou privé ?
  2. Flexbox ou Grid pour un menu horizontal ?
  3. Que vaut notes[notes.length] ?

Trois questions courtes, sans regarder vos notes : la veille, la semaine passée, puis plus loin. Répondez sur une feuille ; la correction suit, à l’oral.

Apport — Vérifier sa page (15 min)

  • Pourquoi : « ma page est accessible » ne se prouve pas à l’œil.
  • Vérifier : un audit, puis le clavier, puis le contraste.

Pourquoi. Certains visiteurs n’utilisent pas de souris, d’autres voient mal les couleurs peu contrastées. Une vérification trouve ce que vous ne voyez pas.

Définition. Vérifier sa page, c’est faire trois contrôles, toujours les mêmes. Lighthouse audite plusieurs catégories, dont la performance, l’accessibilité et le référencement ; dans Chrome, il se lance depuis l’onglet Lighthouse des outils de développement (Google, s. d.-b). Le clavier : Tab passe à l’élément suivant, Maj + Tab au précédent, Entrée active ; le focus doit rester visible. Le contraste : 4,5:1 au moins pour le texte normal (W3C, s. d.).

Avant / après : le même menu, après deux appuis sur Tab. À gauche, le focus est visible ; à droite, outline: none l’a effacé.

Vérifier — attention et vérification

AvertissementAttention

outline: none dans le CSS (souvent pour « faire joli ») rend le focus invisible : au clavier, on ne sait plus où l’on est. Gardez un contour visible, avec :focus-visible. Autre piège : lancez Lighthouse en navigation privée, car les extensions installées faussent les scores.

  • Vérifiez : quelle touche ramène au champ précédent ?

Pas à pas ensemble — Les trois contrôles (50 min)

  1. Lighthouse : le score d’accessibilité.
  2. Le clavier : toute la page, sans souris.
  3. Le contraste : chaque couple texte et fond.
  4. Notez tout, avant de corriger.

Niveau : guidé. Nous le faisons ensemble, chacun sur sa page publiée.

Pas à pas — Lighthouse. Le formateur lance l’audit sur sa page ; vous le refaites aussitôt sur la vôtre.

  1. Ouvrez votre page publiée dans une fenêtre de navigation privée, puis les outils du navigateur (F12).
  2. Onglet Lighthouse ; laissez Analyze page load.
  3. Cliquez sur Run audit ; attendez 30 à 60 secondes.
  4. Lisez le score Accessibility ; dépliez un problème : une explication, en anglais.

Vous devez voir : un score sur 100 ; sous le score, la liste des problèmes. Notez-les sur une feuille.

Le clavier. Le formateur montre chaque étape ; vous la refaites aussitôt.

  1. Cliquez dans la barre d’adresse, puis appuyez sur Tab : le focus entre dans la page.
  2. Continuez avec Tab : chaque lien, chaque champ reçoit un contour visible.
  3. Maj + Tab : vous revenez en arrière.
  4. Remplissez le formulaire sans toucher la souris.

Vous devez voir : un contour visible à chaque étape. Notez ce qui ne reçoit pas le focus.

Le contraste. Avec le sélecteur de couleur des outils du navigateur, comme en semaine 5 (Google, s. d.-a) : le tutoriel de mardi montre l’endroit.

  1. F12, onglet Éléments : cliquez sur un paragraphe.
  2. Dans l’onglet Styles, cliquez sur le petit carré de couleur à côté de color.
  3. Lisez le rapport de contraste.

Vous devez voir : un nombre, avec une coche si le seuil est atteint. Vérifiez aussi le texte du bouton et des liens.

Corriger et republier (30 min)

  1. Corrigez dans dwwm-tp, un problème à la fois ; commitez.
  2. Publiez : cp, puis git push depuis page-perso.
  3. Relancez les contrôles deux minutes plus tard.
  4. Réussi si : accessibilité ≥ 90 ; tout au clavier ; contraste ≥ 4,5:1.
  5. Pas fini ? Vous terminez mercredi 18/11 matin.

Niveau : semi-guidé.

Pas fini ce matin ? Vous terminez mercredi 18/11 matin (semaine 7) : soutien avec le formateur pour ceux qui n’ont pas fini, autonomie pour les autres. Notez ce qui reste à corriger avant de partir.

Problèmes fréquents et pistes : contraste insuffisant ; image sans alt ; champ sans label ; titres qui sautent un niveau ; lien dont le texte ne dit rien (« cliquez ici »). Demandez à CS50.ai d’expliquer un problème signalé, pas de le corriger.

NoteAides
  • Le cours : Vendredi, « Apport — Vérifier sa page ».
  • L’IA : CS50.ai (palier 1) : demandez une explication, pas le code.
  • MDN : Qu’est-ce que l’accessibilité ? ; Accessibilité au clavier ; Contraste de la couleur.

Enregistrer et envoyer (2 min)

Fin du TP : dans le terminal, depuis ~/dwwm/dwwm-tp/semaine-06 :

git status
git add page-perso
git commit -m "Corrige les problèmes signalés par les contrôles"
git push

Réussi si : git status affiche Votre branche est à jour avec 'origin/main' et rien à valider, la copie de travail est propre ; sur GitHub, le commit apparaît dans dwwm-tp. Le message suit la règle de la semaine 4 : ce que fait le commit, à l’impératif, en une ligne (fiche aide-mémoire commit du Drive partagé, ou fiche de révision).

La grille de livraison

  • Tests au vert : page et mise en page.
  • Validateur du W3C : aucune erreur.
  • Lisible à 375 px et sur grand écran, sans défilement horizontal.
  • Palette, espacements et tailles de texte en variables, dans :root.
  • Lighthouse : accessibilité 90 au moins ; tout au clavier.
  • Publiée en HTTPS, sans donnée personnelle superflue.

À retenir — ce matin

AstuceÀ retenir
  • Lighthouse : viser 90 en accessibilité.
  • Clavier : Tab, Maj + Tab, un focus toujours visible.
  • Contraste : 4,5:1 au moins pour le texte.

Si le temps le permet

Le README de livraison, en anglais (niveau : guidé).

  1. README.md à la racine du dépôt public page-perso, en anglais.
  2. Le lien de la page publiée ; les outils et technologies utilisés.
  3. Le score Lighthouse, avant et après.
  4. Trois problèmes corrigés, en une phrase chacun.

Créez-le en ligne de commande, dans ~/dwwm/page-perso, puis écrivez-le dans VS Code. Public lui aussi : aucune donnée personnelle. Exemple de plan : Live site, Built with, Accessibility check (before / after), What I fixed, AI usage (la section « Usage de l’IA » demandée par la charte : outil utilisé et pour quoi faire, ou « none »). Terminez par git add README.md, git commit -m "Ajoute le README de livraison" et git push.

Réussi si : le fichier s’affiche sur la page du dépôt, sans donnée personnelle.

  • L’IA : CS50.ai (palier 1) : demandez une explication, pas le code.
  • MDN : Publier votre site web.
AstuceDéfi

L’extension WAVE : elle pose les problèmes sur la page. Une seule fois : sur le Chrome Web Store, page WAVE Evaluation Tool, cliquez sur Ajouter à Chrome ; puis Ctrl + Maj + U sur votre page publiée (WebAIM, s. d.). Icônes rouges : à corriger ; jaunes : à examiner. Visez aucune erreur.

AstuceDéfi

Sur grand écran, placez chaque label à gauche de son champ : une grille à deux colonnes, dans la media query.

Groupe B en formation de 12 h 45 à 17 h ; le groupe A est au sport (13 h 15 – 16 h).
Pas de notion nouvelle : rien de ce qui se fait ici n’est indispensable pour la suite.

Reprendre le parcours

  • Le parcours d’autonomie de jeudi matin.
  • Reprenez à la ligne où vous vous êtes arrêté.
  • Puis le README de ce matin, s’il reste à faire.
  • Un commit par exercice réussi ; git push à la fin.

Le détail, les critères de réussite, les aides et la méthode si l’on bloque sont dans le parcours d’autonomie. Une seule différence : le formateur est là cet après-midi, demandez-lui plutôt que de noter la question.
