Compétences visées : C4 · communiquer en anglais · apprendre en continu
Livrable : votre dépôt public explorateur-musees, avec l’histoire US-1 fusionnée dans main par une Pull Request.

ImportantLe minimum du jour
  • La première étape du projet, faite avec le groupe : le dépôt public, le premier commit, la branche us-1-liste.
  • Le palier 1 : l’histoire US-1 (la liste) livrée par une Pull Request relue avec la grille, puis fusionnée.

Les paliers 2 et 3, puis la rubrique « Si le temps le permet », sont la suite naturelle, pour ceux qui avancent.

Objectifs

  • Démarrer un projet dans son propre dépôt GitHub public, avec un premier commit propre.
  • Livrer une histoire du backlog par le GitHub Flow : une branche, des commits, une Pull Request relue, une fusion.
  • Relire son propre code avec une grille, avant de le fusionner.

Comment se passe l’après-midi. Le projet n° 1 commence. Une seule notion : le GitHub Flow, la façon de livrer chaque histoire. Les branches et les Pull Requests datent de la semaine 4 ; le code de l’histoire US-1, de lundi. D’abord la présentation du projet, puis une démonstration du GitHub Flow, puis la première étape tous ensemble, en live coding avec le formateur. Ensuite, vous continuez seuls.

Après-midi — Lancement du projet n° 1

Le projet n° 1 : l’Explorateur des musées (10 min)

  • Une page pour parcourir les 34 musées de France de Bretagne.
  • Rechercher, voir le détail ; puis les données de l’API (semaine 9).
  • Un dépôt public, rien que pour le projet.
  • 2 semaines et demie ; défense orale en semaine 11.

Le besoin. Un office de tourisme veut une page simple pour faire découvrir les musées de France de la région : la liste, une recherche par nom ou par ville, le détail d’un musée. Les données viennent de la base Muséofile du ministère de la Culture, publiée en données ouvertes (Ministère de la Culture, s. d.), sous Licence Ouverte (Etalab, s. d.). Ce ne sont pas les données de la semaine 7 : une autre région (la Bretagne, et non le Grand Est) et un autre jeu de données, l’annuaire des musées, sans les chiffres de fréquentation.

Le périmètre minimum, ce que chacun livre :

  1. la liste des musées (US-1) ;
  2. la recherche par nom ou par ville (US-2) ;
  3. le détail d’un musée (US-3) ;
  4. les données lues dans l’API, et non plus dans la copie figée (US-4, semaine 9) ;
  5. les quatre états : chargement, erreur, vide, succès (US-5, semaine 9) ;
  6. les tests fournis au vert, et la publication du site (US-6, semaine 11).

Pour ceux qui avancent (palier 3) : compter les musées par département (aujourd’hui) ; garder ses musées favoris (semaine 9, vendredi, avec localStorage).

Le calendrier. Aujourd’hui, US-1 et US-2 ; vendredi après-midi (groupe B) et mercredi prochain, US-3 ; jeudi 03/12, l’API et les quatre états ; semaine 10, les tests avec Vitest et la revue de sprint ; lundi 14/12, la publication ; jeudi 17/12, la défense orale.

Le backlog. Les histoires utilisateur (user stories) sont écrites pour vous dans projet-1/BACKLOG.md, le backlog du projet : « En tant que visiteur, je veux… afin de… », avec un critère d’acceptation. Lisez-les avant le live coding (5 min).

L’API du projet. Les données viennent de l’API tabulaire de data.gouv.fr (data.gouv.fr, s. d.), ouverte, sans clé. Jusqu’à la semaine 9, la page lit une copie figée de sa réponse (data/musees-bretagne.js) : on apprend une chose à la fois. Le fichier api.js est déjà écrit : il construit l’adresse de la requête, toujours bien formée, et vous ne le modifiez pas. data/musees-bretagne.json est la copie de secours, au format exact de l’API : elle servira si l’API ne répond pas, et le jour de la défense. Si un jour la console affiche TypeError: Failed to fetch, ce n’est pas votre code : le réseau, ou le serveur de l’API, a refusé la requête (fiche « Lire un message d’erreur »).

Le GitHub Flow (15 min)

  • Une branche par histoire ; main reste toujours fonctionnelle.
  • Pull Request : vous relisez votre code avec une grille.
  • Fusion dans main, puis git pull.

Pourquoi. Dans une équipe, personne ne travaille directement sur main : elle doit toujours marcher, parce qu’elle est publiée. Chaque changement passe par une branche et une relecture. Dans le projet n° 1, vous êtes seul : vous vous relisez vous-même, avec une grille. Au projet n° 3, en binôme, c’est votre binôme qui relira.

Définition. Le GitHub Flow est une façon de travailler en quatre temps : une branche par changement ; des commits poussés sur cette branche ; une Pull Request qui propose de fusionner, relue avant d’être acceptée ; la fusion dans main (GitHub, s. d.). Un code smell est un signe, dans le code, qu’il pourrait être écrit plus simplement : la grille en cherche trois (Refactoring Guru, s. d.).

Le GitHub Flow, en image

Le texte du schéma : main reçoit le premier commit (.gitignore, .env.example, README.md). La branche us-1-liste part de main, reçoit deux commits, puis revient dans main par une fusion. Quatre étapes : 1. une branche par histoire ; 2. des commits poussés ; 3. une Pull Request, relue avec la grille ; 4. la fusion, puis git pull.

Le GitHub Flow, l’exemple minimal

git switch -c us-1-liste
git add logic.js app.js
git commit -m "Affiche la liste des musées (US-1)"
git push -u origin us-1-liste
# Sur GitHub : Pull Request, relecture, fusion
git switch main
git pull

Toutes ces commandes datent de la semaine 4 ; ce qui est nouveau, c’est leur ordre, à chaque histoire. git push -u origin us-1-liste envoie la branche sur GitHub (-u : les git push suivants de cette branche n’ont plus besoin du nom). Sous macOS, si le # de la ligne de commentaire est refusé par le terminal, tapez d’abord setopt interactivecomments (ou ne tapez pas cette ligne : c’est une note).

Live coding — La première étape, tous ensemble (75 min)

  • Le formateur projette, vous faites en même temps, une étape à la fois.
  • Code et commentaires tapés, comme dans chaque pas à pas.
  • Vérifiez « Vous devez voir » à chaque étape.
  • Perdu ? Levez la main : on ne laisse personne derrière.

Étape 6 — La logique de US-1 (10 min). Dans logic.js, remplacez la fonction museumLabel par celle-ci, avec la décomposition de mardi dans les paramètres :

// Décomposition dans les paramètres : name et city
export function museumLabel({ Nom_officiel: name, Ville: city }) {

Puis lancez seulement le test de US-1 : --test-name-pattern ne lance que les tests dont le nom contient ce mot.

Étape 7 — L’affichage de US-1 (12 min). Dans app.js, sous les deux lignes import, supprimez la ligne console.log('À faire', …), puis tapez :

explorateur-musees/app.js
// Le résumé de la page
const summary = document.querySelector('#resume');
// La liste de la page, vide pour l'instant
const list = document.querySelector('#liste');
// Le nombre de musées, dans le résumé
summary.textContent = `${MUSEUMS.length} musées`;

  // Un nouveau <li>
  const item = document.createElement('li');
  // Son texte vient de la logique : museumLabel

  list.append(item);
}

Vous devez voir : « Musées de Bretagne », un champ de recherche (qui ne fait encore rien), « 34 musées », puis 34 lignes ; aucune erreur dans la console.

Étape 10 — La fusion (5 min). Merge pull request, Confirm merge. Puis, dans le terminal :

git switch main

Vous devez voir : sur GitHub, la PR marquée Merged ; dans le terminal, la liste des fichiers arrivés sur main. git log --oneline affiche le commit de US-1.

La grille de relecture (5 min)

  • Les tests de l’histoire passent ; npx eslint . : aucune erreur.
  • Aucun innerHTML ; aucune donnée personnelle.
  • Trois code smells : nom vague, fonction trop longue, code dupliqué.

Recopiez cette grille dans la description de chaque Pull Request, et cochez chaque ligne (- [x]) après l’avoir vérifiée dans l’onglet Files changed :

- [ ] Les tests de l'histoire passent (node --test …)
- [ ] npx eslint . n'affiche aucune erreur
- [ ] Aucun innerHTML (vendredi : pourquoi)
- [ ] Aucune donnée personnelle, aucun secret
- [ ] Pas de nom vague (data, x, truc) : chaque nom dit ce qu'il contient
- [ ] Pas de fonction trop longue : une fonction, une tâche
- [ ] Pas de code dupliqué : deux blocs identiques deviennent une fonction

Les trois dernières lignes sont des code smells : des signes qu’un code pourrait être plus simple, sans être faux (Refactoring Guru, s. d.). Un code smell n’empêche pas la fusion : notez-le dans la PR, et corrigez-le dans une prochaine histoire.
